### Pro Tips

**Quick tip — Diagnostic Printing is Key.**
Don't just print the variable: `print(my_variable)`. Instead, print *what* it is and *where* you are. This saves massive debugging time.
```python
# Bad
print(user_data) 

# Good (Use f-strings for clean formatting!)
print(f"DEBUG: Processing user {user_id} in login_check function. Data: {user_data}")
```

**Pro move: Control your output flow with `end` and `sep`.**
The `print()` function defaults to adding a newline character (`\n`) at the end. If you're building output sequentially or need things to stay on the same line, use the `end=' '` argument. Similarly, use `sep=' | '` to define how multiple arguments are separated without manually concatenating strings.

**Here's something most tutorials skip: Know your streams.**
In real development environments (servers, CI pipelines, containers), there are two main output streams: Standard Output (`stdout`) and Standard Error (`stderr`). `print()` defaults to `stdout`. Use `stderr` (via the `sys` module) specifically for logging errors or warnings, so they don't pollute the actual data output intended for downstream processing or reports.

### Mentor Moment

Hey, can I tell you about the time I spent three hours debugging a simple logging issue on a production server?

Quick story from my first job: I was working on a nightly script that processed thousands of financial transactions. This script would run, print the resulting data, and then exit. If it failed, it was supposed to print an error message. Since I was only concerned with *seeing* the output, I used the basic `print()` function for *everything*—the successful data, the status updates, and the error messages.

The environment was set up to pipe the script’s primary output (`stdout`) into a large data file for later analysis.

One night, the script silently started failing about halfway through. I could see the resulting data file was incomplete, but I couldn't find the error in the logs. Why?

The error message I was printing—the critical alert that the external API had timed out—was being mixed right into the 100,000 lines of successfully processed data in the main output file. Searching that massive file for a single `API Error` line felt like searching for a grain of sand on the beach. Furthermore, our automated monitoring system, which was only scanning the *error log* file, never saw the failure because the message went to the *data* file instead.

#### The Lesson: Standard Output vs. Standard Error

In programming, we generally deal with two main channels, or "streams," for communication:

1.  **Standard Output (`stdout`):** This is for the *intended result* of your program—the calculated data, the successful report, the clean output you plan to pipe to another program or save as a final result. This is where basic `print()` sends data.
2.  **Standard Error (`stderr`):** This is for *metadata* about the program's execution—errors, warnings, diagnostics, and debugging messages.

If you don't differentiate, your data output gets mixed with your debugging noise, making automation, monitoring, and troubleshooting nearly impossible.

**The Fix:** When printing errors or diagnostics that should *not* be part of the final data output, you need to redirect it.

```python
import sys

# Data that is the primary result goes to stdout (default print)
print("Transaction successful: Data line 42")

# Critical error/diagnostic information goes to stderr
print("ERROR: Connection timed out!", file=sys.stderr) 
```

#### Career Relevance

This knowledge separates the juniors who write code that runs locally from the seniors who write code that runs reliably in production systems (like Docker containers, Kubernetes, or CI pipelines). Every logging tool, monitoring system, and production pipeline relies on this fundamental separation of streams to correctly capture and alert on failures. Mastering basic printing isn't about syntax; it's about mastering how your code communicates with the outside world.

**Interview Gotcha:**
> "If an interviewer asks, 'How would you print an error message in a way that separates it from the primary data output?' they're really testing whether you understand **I/O streams (stdout vs. stderr)**. Here's how to nail it: Talk about importing the `sys` module and using the `file=sys.stderr` argument in the `print` function. Mentioning that `print` defaults to `sys.stdout` shows you understand the mechanics, not just the usage."

#### Hard (Interview Level, 30-45 min): Stream Separation

Write a function, `check_status(data, threshold)`, that takes a dictionary of sensor data and a minimum threshold value.

1.  Iterate through the `data`.
2.  If any sensor value is below the `threshold`, print an **ERROR** message to the *Standard Error* stream (`sys.stderr`). The message should include the sensor name and its failing value.
3.  If all sensors are above the `threshold`, print a single **SUCCESS** message to the *Standard Output* stream.

```python
import sys

sensor_readings = {
    "temp_a": 88,
    "temp_b": 72,
    "pressure_1": 45,
    "humidity": 60
}

# Run the function with a threshold of 75
check_status(sensor_readings, 75) 
```

**Expected Output (Note: The first two lines should visually appear, but they are technically written to the error stream):**
> ERROR: temp_b reading (72) is below threshold 75.
> ERROR: pressure_1 reading (45) is below threshold 75.
> System Health Check: SUCCESS.
